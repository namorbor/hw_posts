# REST API для блога

Дипломный проект: регистрация и вход пользователей, создание и чтение постов и комментариев. За основу взят [шаблон проекта](https://github.com/netology-code/go-template-dip), адаптированный под JSON-хранилище и требования задания. HTTP-сервер написан на `net/http`, пароли хешируются bcrypt, авторизация использует JWT HS256.

## Требования

- Go 1.25 или новее — версия, необходимая выбранным зависимостям.
- Docker и Docker Compose для запуска в контейнере.
- curl; Python 3 нужен только для извлечения значений из JSON в примерах и проверочном скрипте.

## Локальный запуск

Из корня проекта:

```bash
cp .env.example .env
go mod download
go run main.go
```

API доступно по адресу `http://localhost:8080`. Для остановки нажмите `Ctrl+C`.

Чтобы токены продолжали действовать после перезапуска, сгенерируйте секрет командой `openssl rand -hex 32` и запишите результат в `JWT_SECRET` в `.env`. При пустом значении сервер создаёт временный ключ; после перезапуска потребуется снова войти.

### Конфигурация

Переменные окружения имеют приоритет над `.env`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `8080` | Порт HTTP-сервера, от 1 до 65535 |
| `DATA_DIR` | `data` | Каталог JSON-файлов |
| `LOG_FILE` | `log.txt` | Файл событий |
| `JWT_SECRET` | пустое значение | Ключ подписи JWT, минимум 32 байта; при отсутствии создаётся временный |
| `JWT_TTL_HOURS` | `24` | Срок действия токена в часах, от 1 до 720 |

## Запуск через Docker Compose

Подготовьте `.env`, как описано выше, и выполните:

```bash
docker compose up --build -d
docker compose ps
curl http://localhost:8080/health
docker compose logs -f blog
```

Ответ проверки состояния: `{"status":"ok"}`. Для выхода из просмотра логов нажмите `Ctrl+C`.

```bash
# Посмотреть отложенные события
docker compose exec blog cat /app/logs/log.txt

# Остановить приложение
docker compose down
```

JSON-файлы и журнал сохраняются в именованных томах `blog-data` и `blog-logs`. Обычный `docker compose down` сохраняет эти данные для следующего запуска. В контейнере используются пути `/app/data` и `/app/logs/log.txt`; `PORT` из `.env` задаёт порт на компьютере, внутренний порт всегда 8080. Локальный запуск и Docker используют отдельные хранилища.

## API

Все ответы имеют формат JSON. Для запросов с телом нужен заголовок `Content-Type: application/json`. Авторизация передаётся как `Authorization: Bearer <token>`.

| Метод и путь | Тело запроса | Токен | Успешный ответ |
|---|---|---|---|
| `POST /register` | `username`, `email`, `password` | Нет | `201`, пользователь |
| `POST /login` | `email`, `password` | Нет | `200`, `token`, `expires_at`, `user` |
| `POST /posts` | `title`, `content` | Да | `201`, пост |
| `GET /posts` | — | Нет | `200`, массив постов |
| `GET /posts/{id}` | — | Нет | `200`, пост |
| `POST /posts/{id}/comments` | `text` | Да | `201`, комментарий |
| `GET /posts/{id}/comments` | — | Нет | `200`, массив комментариев |
| `GET /health` | — | Нет | `200`, `{"status":"ok"}` |

Поля объектов:

- Пользователь: `id`, `username`, `email`, `created_at`. Пароль и его хеш в ответ не включаются.
- Пост: `id`, `author_id`, `title`, `content`, `created_at`.
- Комментарий: `id`, `post_id`, `author_id`, `text`, `created_at`.

Даты записываются в UTC в формате RFC 3339. Автор определяется по токену, пост комментария — по URL. Пустые списки возвращаются как `[]`.

### Валидация и ошибки

`username` содержит 3–50 символов: буквы, цифры, `_`, `-`, `.`. Email должен быть корректным адресом длиной до 254 байт. Email и username уникальны без учёта регистра; пробелы по краям удаляются. Пароль содержит минимум 8 символов и максимум 72 байта.

Поля `title`, `content`, `text` обязательны и не могут состоять из пробелов. Ограничения: заголовок — 200 символов, содержимое поста — 100 000, комментарий — 1 000. Максимальный размер тела запроса — 1 МиБ. Неизвестные поля и несколько JSON-значений в одном теле отклоняются.

Ошибки возвращаются в виде `{"error":"сообщение об ошибке"}`:

| Код | Причина |
|---|---|
| `400` | Некорректный JSON, поля или ID |
| `401` | Неверные данные входа, отсутствующий, неверный или истёкший токен |
| `404` | Пост или маршрут не найден |
| `405` | Метод не поддерживается; допустимые методы перечислены в `Allow` |
| `409` | Email или username уже занят |
| `413` | Тело запроса превышает 1 МиБ |
| `415` | Неверный или отсутствующий `Content-Type` |
| `500` | Внутренняя ошибка, например ошибка записи данных |
| `503` | Сервер завершает работу и больше не принимает новые запросы |

### Пример полного сценария

Команды выполняются во втором терминале при запущенном сервере. При повторной регистрации того же пользователя ожидается `409`; можно перейти к входу.

```bash
BASE_URL=http://localhost:8080

curl -sS "$BASE_URL/health"

curl -sS -X POST "$BASE_URL/register" \
  -H 'Content-Type: application/json' \
  -d '{"username":"demo","email":"demo@example.com","password":"password123"}'

LOGIN_RESPONSE=$(curl -sS -X POST "$BASE_URL/login" \
  -H 'Content-Type: application/json' \
  -d '{"email":"demo@example.com","password":"password123"}')
printf '%s\n' "$LOGIN_RESPONSE"
TOKEN=$(printf '%s' "$LOGIN_RESPONSE" | python3 -c 'import json,sys; print(json.load(sys.stdin)["token"])')

POST_RESPONSE=$(curl -sS -X POST "$BASE_URL/posts" \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"title":"Первый пост","content":"Текст публикации"}')
printf '%s\n' "$POST_RESPONSE"
POST_ID=$(printf '%s' "$POST_RESPONSE" | python3 -c 'import json,sys; print(json.load(sys.stdin)["id"])')

curl -sS "$BASE_URL/posts"
curl -sS "$BASE_URL/posts/$POST_ID"

curl -sS -X POST "$BASE_URL/posts/$POST_ID/comments" \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"text":"Первый комментарий"}'

curl -sS "$BASE_URL/posts/$POST_ID/comments"
```

## Хранение и логирование

В `DATA_DIR` автоматически создаются `users.json`, `posts.json`, `comments.json`. Изменения сохраняются до отправки успешного ответа: временный файл записывается целиком, синхронизируется и заменяет исходный. Мьютекс защищает записи от одновременных запросов. Повреждённые данные приводят к ошибке запуска. Одну папку данных должен использовать только один экземпляр сервера.

HTTP-запросы и ошибки выводятся в консоль. После создания поста или комментария строка события отправляется в канал. Отдельная горутина собирает накопившиеся события и записывает их в `log.txt` после паузы в 1 секунду; новые события за время паузы попадают в следующую группу. Обычная задержка составляет 1–2 секунды. Пример журнала:

```text
2026-11-05T10:00:01Z user 1 created post 1
2026-11-05T10:00:02Z user 1 created comment 1
```

При `SIGINT` или `SIGTERM` сервер завершает текущие запросы, закрывает канал, дописывает очередь и закрывает файл. Это работает при `Ctrl+C` и штатной остановке Docker Compose.

## Структура и проверки

```text
main.go              — запуск и завершение сервера
internal/config/     — переменные окружения
internal/model/      — пользователь, пост, комментарий
internal/storage/    — JSON-хранилище
internal/handler/    — маршруты, авторизация и обработчики HTTP
internal/logger/     — канал и горутина записи событий
pkg/auth/            — bcrypt и JWT
scripts/smoke.sh     — проверка работающего API через curl
```

```bash
go test -race ./...
go vet ./...

# Сервер должен быть запущен; скрипт создаёт тестового пользователя, пост и комментарий
bash scripts/smoke.sh
# Для другого порта:
BASE_URL=http://localhost:8090 bash scripts/smoke.sh
```

Тесты проверяют сценарии API, валидацию, авторизацию, сохранение и загрузку данных, параллельные записи, ошибки хранилища и завершение логгера.
